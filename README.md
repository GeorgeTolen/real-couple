# CQA: оценка качества диалогов Freedom Broker

Прототип Conversation Quality Analytics для хакатона. Система оценивает работу оператора в чатах и звонках на RU, KZ и EN по настраиваемому чек-листу. Она показывает баллы, объяснение и реплики-доказательства, принимает апелляции и пересчитывает итог после решения проверяющего.

## Запуск

Нужны Python 3.12+ и ключ [OpenRouter](https://openrouter.ai). Node не нужен: собранный интерфейс лежит в `frontend/dist`. Для метрик речи по записи нужен ffmpeg, без него система считает метрики только по транскрипту.

```bash
cp .env.example .env        # впишите OPENROUTER_API_KEY и ORGANIZER_API_URL
make install
make import                 # 65 диалогов DEV из API организаторов
make evaluate-all           # оценка всех диалогов, около $1,6 и 10 минут
make run                    # http://localhost:8000, документация API на /docs
```

База не входит в репозиторий, поэтому до импорта список диалогов пуст. Импортировать набор и запустить оценку можно и из интерфейса, на экране «Оценка». Готовые результаты лежат в `results/dev/results.json`.

`ORGANIZER_API_URL` это адрес кнопки «Открыть GET для DEV» со стр. 3 гайда организаторов, без параметра `group_id`. Данные организаторов и сам гайд в репозиторий не входят: в них есть ссылки на записи реальных звонков, которые открываются без пароля. Диалоги загружаются по API командой импорта, а тесты работают на синтетических чатах.

Если `make` нет (например, в Windows), команды те же:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r backend\requirements.txt
cd backend
$env:PYTHONUTF8=1
..\.venv\Scripts\python -m uvicorn app.main:app --port 8000
```

Или через Docker:

```bash
docker build -t cqa . && docker run -p 8000:8000 --env-file .env cqa
```

## Модели и стоимость одной оценки

Оценка идёт через OpenRouter. Использованы платные модели.

| Роль | Модель |
|---|---|
| Судья A | `google/gemini-3.8-flash` |
| Судья B | `openai/gpt-6.1-sol` |
| Арбитр, только по спорным критериям | `google/gemini-4-argon` |
| Локальный режим, необязательно | Gemma 4 26B-A4B через Ollama, задаётся в `LOCAL_MODEL` |

Стоимость одной оценки со всеми вызовами, замер на 65 диалогах DEV:

| Показатель | Значение |
|---|---|
| Средняя стоимость диалога | около $0,025 |
| Без расхождений судей | около $0,018 |
| Самая дорогая оценка, звонок с арбитром | около $0,056 |
| Весь DEV | около $1,6 |

Стоимость и токены каждой оценки видны в карточке диалога на вкладке «Детали».

## Точность

Команда `make bench` сравнивает оценку с ручной разметкой 12 диалогов DEV из `bench/gt_manual.json`. Пункты, помеченные как спорные, в точность не входят.

| Показатель | Результат | Порог |
|---|---|---|
| Совпадение по критериям | 98,9% (86 из 87) | от 95% |
| Средняя ошибка итога | 3,78 балла | до 5 |
| Совпадение ответов между двумя прогонами | 99,0% (95 из 96) | от 98% |

Отдельно есть контрольный набор вне калибровки: 10 новых чатов, эталон закоммичен до первого запуска моделей, а подсказки после него не менялись. Команда `make holdout`, отчёт в `bench/holdout/holdout_report.json`.

| Контрольный набор | Результат |
|---|---|
| Совпадение по критериям | 97,2% (69 из 71) |
| Средняя ошибка итога | 4,30 балла |
| Согласие с эталоном, каппа | 0,96 (у людей между собой около 0,80) |
| Время на 10 диалогов | 83 секунды |

Эти чаты написал автор системы, поэтому они легче реальных и независимость у них неполная.

Оценка по 12 диалогам оптимистична. Подсказки в чек-листе калибровались на этих же 12 диалогах, а разметку делал один человек. Ошибка итога считается и по спорным пунктам, где эталон это лучшая догадка разметчика. Стабильность проверяет `bench --repeat 2`, замер сделан на тех же 12 диалогах.

## Почему именно так

LLM-as-a-Judge стал основным способом оценивать тексты моделью, но у судей-моделей есть систематические перекосы:

- **Позиционный.** Порядок вариантов меняет ответ (Wang и др., arXiv 2305.17926).
- **Перекос на длину.** Судья предпочитает длинный и гладкий ответ (MT-Bench, arXiv 2306.05685).
- **Нестабильность.** На одних и тех же входных данных модель выдаёт разные решения.

Потолок задачи это согласие людей между собой, каппа около 0,80 (NVIDIA, arXiv 2510.09738).

Исследования изучали парное сравнение. У нас рубрика из 8 критериев с весами, поэтому перекос проявляется в выборе ступени шкалы и зависит от формулировок. Главной целью были стабильность и честность, поэтому каждое снижение должно опираться на конкретную реплику.

**Пример нестабильности.** Диалог `p1-en-006` при первом прогоне получил 85,00, при втором 80,50. Оба судьи оба раза ставили по «Ведению диалога» 10 и 7, а арбитр выбирал то одно, то другое. Помогли три меры:

- кеш результата;
- проверка согласованности по правилу «нет сбоя с номером реплики, нет снижения»;
- обязательный арбитр при споре.

После этого повторный прогон совпал в 95 ответах из 96.

**Выбор моделей.** 16 моделей через OpenRouter прошли одну и ту же оценку на 12 размеченных диалогах DEV: 6 RU, 3 KZ, 3 EN. Полная таблица лежит в `docs/pitch/data/model_benchmark.json`.

| Модель | Точность | $ за диалог | Роль |
|---|---|---|---|
| `openai/gpt-6.1-sol` | 97,7% | 0,0083 | судья B |
| `google/gemini-3.8-flash` | 96,2% | 0,0089 | судья A |
| `google/gemini-4-argon` | 95,4% | 0,0120 | арбитр |
| `anthropic/claude-opus-5.5` | 94,0% | 0,0336 | дороже в 4 раза |
| `google/gemma-4-26b-a4b-it` | 83,9% | 0,0004 | локальный режим |
| `openai/gpt-oss-20b` | 70,1% | 0,0002 | открытые веса, 8 ГБ |
| `ibm-granite/granite-4.2-8b` | 66,7% | 0,0002 | открытые веса, 8 ГБ |
| `mistralai/ministral-8b-2512` | 62,1% | 0,0003 | открытые веса, 8 ГБ |
| `qwen/qwen3.5-9b` | 61,6% | 0,0002 | открытые веса, 8 ГБ |

Модели с открытыми весами, которые помещаются на ноутбук с 8 ГБ, подходят, когда данные не должны уходить наружу. Для эталонной точности их мало. Судьи взяты от разных вендоров, Google и OpenAI, чтобы их ошибки не совпадали.

**Вес слов.** До модели код фиксирует факты:

- кто ответил первым;
- паузы дольше 180 секунд;
- формальное приветствие или нет;
- эскалация;
- подтверждение личности.

Модель видит эти факты вместе с транскриптом.

**Пример: `p1-ru-014` и `p1-ru-013`.** Клиент в обоих задал один и тот же вопрос, где найти раздел на сайте. Оператор оба раза решил его двумя репликами, консультация 20 из 20. Но у `p1-ru-014` итог 38,13, а у `p1-ru-013` 100. У `p1-ru-014` баллы ушли так:

| Что было | Что снизилось |
|---|---|
| «Привет» вместо приветствия с именем | контакт |
| Повторный вопрос о том, что клиент уже написал боту | выявление потребности и ступень ведения диалога |
| «Понял» в ответ на «я уже писал» | эмпатия |
| «Хорошего дня» без итога | завершение |

У каждого снижения есть номер реплики.

## Как устроена оценка

```
API организаторов или файл
   → нормализация: номера реплик с 1, секунды от начала, исходные метки сохраняются
   → факты о диалоге: первая реплика, приветствие, паузы, закрытие, метрики речи
   → промпт и JSON Schema генерируются из версии чек-листа
   → судья A и судья B параллельно
        совпали → ответ
        разошлись → арбитр по спорным критериям, флаг «На проверку»
   → баллы считает код (scoring.py), а не модель
   → SQLite: исходная оценка, апелляции, решения; финальный итог считается из них
   → интерфейс и results.json
```

- **Новый критерий работает без правки кода.** Чек-лист это конфигурация: критерии, веса, типы, шкалы, условия N/A, формулировки для звонков. Промпт, схема ответа и расчёт строятся из неё.
- **Версии неизменяемы.** Любая правка создаёт новую версию, оценка хранит номер своей версии.
- **Честность процесса.** В коде нет результатов и правил по `conversation_id`. Сырые ответы всех моделей сохраняются и видны в карточке на вкладке «Детали».
- **Расчёт.** N/A исключает критерий и перераспределяет вес, округление до двух знаков половиной вверх. Грубая ошибка передаётся отдельным флагом и не обнуляет итог.
- **Официальные трактовки.** Ответы организаторов вынесены в подсказки чек-листа: прощание без итога и предложения помощи это «Нет», клиент сразу дал все детали это N/A, раскрытие данных до идентификации это идентификация «Нет» и грубая ошибка «Да». База знаний участникам не выдана, поэтому модель не придумывает факты и пишет, что факт не проверялся.
- **Переоценка после правки чек-листа.** По умолчанию модель спрашивают только об изменённых критериях, остальные ответы берутся из прошлой версии. Смена веса не требует модели совсем: итог пересчитывается сразу и бесплатно. Полная переоценка остаётся опцией на экране запуска.
- **Одинаковый результат при повторе.** Тот же диалог с той же версией чек-листа, промптом и моделями отдаёт сохранённую оценку без вызова моделей. Пересчёт заново запускается отдельной кнопкой, показывает, что изменилось и почему, а прошлая оценка остаётся в истории.
- **Флаг «На проверку».** Ставится, только если арбитр не согласился ни с одним судьёй, арбитр или судья был недоступен, либо сбой так и не был назван.
- **Карта диалогов.** Ось X «Решение вопроса» и ось Y «Сервис» считаются тем же кодом, что итог: взвешенная доля по критериям оси, N/A исключается. Ось критерия можно сменить в редакторе, модель при этом заново не спрашивается.
- **Цифры на экране запуска.** Точность и цена читаются из файлов `bench/results_<режим>.json` и `bench/holdout/holdout_report.json` вместе с датой и числом диалогов. Нет файла замера, значит на экране «нет замера».
- **Нет сбоя, нет снижения.** Если модель ставит не максимальную ступень и не называет сбой с номером реплики, этот критерий запрашивается повторно. Расхождение судей решает арбитр. Если он недоступен, ступень берётся у судьи с названным сбоем, а без сбоя ставится верхняя.
- **Страховка от пропуска грубой ошибки.** Если судья ответил «Нет» по идентификации, а по грубым ошибкам стоит «Нет», этот ответ проверяет арбитр. Правило задано в `review_rules` чек-листа.
- **Звонки.** Запись отдаётся с перемоткой, свежая ссылка на файл запрашивается при скачивании. Время реплики в записи считается с учётом начала и пауз записи.

## Сценарий демо на 5 минут

1. **Интерфейс и диалог.** Список диалогов, фильтры, экран «Грубые нарушения» с типом, цитатой и объяснением, диалог `p1-ru-009`.
2. **Оценка.** Блок «Почему снижена оценка» и кнопка «Перейти к фрагменту». Раскрыть «Идентификация», нажать чип `#N` и перейти к реплике. Показать критерий с N/A и причиной, итог и секции.
3. **Апелляция.** «Оспорить критерий», комментарий, отправить. Переключить роль на «Проверяющий», открыть «Апелляции», выбрать «Изменить», указать причину. Показать пересчёт итога и исходную оценку в карточке.
4. **Изменение чек-листа.** «Чек-листы»: добавить критерий, изменить существующий или поменять вес, «Сохранить как версию», «Применить к диалогам», запустить на выбранных диалогах.

## Час контроля

Одна команда: импорт, оценка, экспорт, проверка формата, коммит и пуш `results/prod/results.json` в `main`.

```bash
make prod GROUP=<id контрольного набора>
```

Без `make`:

```powershell
cd backend
$env:PYTHONUTF8=1
..\.venv\Scripts\python -m app.cli prod --group <id>
```

После выполнения проверьте лог проверки и наличие коммита на GitHub. Диалоги с ошибкой модели команда повторяет один раз автоматически. Если ошибки остались, они попадут в файл со `status: "error"`, и команду можно запустить снова: она оценит только недостающие.

На репетиции 10 диалогов с пустой базой заняли 6 минут 12 секунд и $0,24. Обычно диалог занимает до минуты, но один завис и ждал таймаут запроса. Закладывайте на прогон 10 минут.

Репетиция без коммита и пуша, файл пишется в `data/rehearsal/`:

```bash
make rehearsal GROUP=DEV
```

Запасной путь через интерфейс: «Оценка», `group_id`, «Импортировать набор», «Запустить оценку», затем блок «Файл для сдачи results.json». Файл после этого нужно закоммитить и отправить вручную.

### Какая версия чек-листа идёт в файл

В файл идут оценки конкретной версии, а не последняя оценка диалога. По умолчанию берётся последняя версия, совпадающая с таблицей организаторов по кодам, весам, шкалам и правилам N/A, поэтому правки для демо в сдачу сами не попадают. Если критерий переименован, его код снимается: новый критерий не попадёт в файл под чужим кодом, а экспорт такой версии будет отклонён с понятной причиной. Если это тот же критерий организаторов с уточнённой формулировкой, код можно выбрать заново в редакторе.

В файл идут ответы модели, а не решения проверяющих: организаторы сравнивают с эталоном работу системы, а тестовая апелляция на демо не должна менять сдачу. Решения можно включить флагом `--with-decisions`.

Перед записью файл проверяется дважды: формат по правилам приложения, затем сверка с данными. Сверка смотрит, что ID существует, номера реплик не выходят за транскрипт, а итог совпадает с пересчётом.

## Распознавание звонков через Whisper

Кнопка «Перераспознать запись» в карточке звонка запускает Whisper large-v3 на этом компьютере и показывает его текст рядом с расшифровкой организаторов. Это необязательно: без установки всё остальное работает.

```bash
make install-whisper
make whisper                # или кнопка в карточке звонка
```

Модель занимает около 3 ГБ и скачивается при первом запуске. На RTX 5070 Ti запись длиной 6 минут распознаётся примерно за 30 секунд. Без видеокарты Whisper работает на процессоре, но намного медленнее.

- **Спикеры.** Запись одноканальная, отдельного разделения по голосам нет. Слова привязываются к репликам организаторов сравнением текстов и времени, поэтому нумерация не меняется. На искажённых коротких репликах привязка может ошибаться.
- **Оценка не меняется.** Баллы и `results.json` считаются по расшифровке организаторов.
- **Персональные данные.** В записи звучат имена и данные, которые организаторы скрыли масками. Текст Whisper по умолчанию скрыт в карточке. Всё услышанное на месте маски заменяется этой маской, а слова вне текста организаторов с цифрами или с большой буквы заменяются на `[Скрыто]`. Сырые слова не сохраняются, результат лежит только в `data/whisper`, не попадает в git и не отправляется в облачные модели. Это эвристика, полного скрытия она не гарантирует, поэтому перед показом просмотрите текст.

## Проверка интерфейса

Сценарии браузера лежат в `frontend/e2e`. Они поднимают отдельный сервер на копии базы, поэтому рабочие оценки и апелляции не меняются. Нужны готовая база `data/cqa.sqlite` и ключ OpenRouter: один сценарий спрашивает модель об одном критерии, это несколько центов. Скриншоты всех экранов сохраняются в `docs/screens`.

```bash
cd frontend
npm install
npm run e2e
```

## Встраивание в Dynamics 365

Интерфейс собирается в один файл `frontend/dist/index.html` на React и Fluent UI v9, с hash-роутингом и относительными адресами API. Его можно разместить как HTML web resource, а компоненты перенести в PCF virtual control. API должно быть доступно с того же адреса или через обратный прокси.

## Ограничения

- Ступени «Консультации» организаторы не уточняли, это остаётся самым спорным критерием. Подсказки чек-листа меняются без правки кода.
- PDF организаторов с чек-листом не входит в репозиторий. Тексты критериев взяты из `docs/PROMPT_stage3_backend.md`.
- Дикция и интонация не оцениваются. По записи считаются только длительность, паузы и темп. Темп и перебивания это оценка по меткам времени транскрипта.
- Имя оператора определяется по его реплике и служит только для отображения. Если оператор не представился, в списке стоит «Не определён».
- В данных нет даты чатов, поэтому в списке для них показана только длительность.
- Локальный режим реализован, но на полном наборе не проверялся. Точность из таблицы выбора модели (91,1%) получена через OpenRouter, а не на локальном запуске.
- Запись одноканальная, поэтому дорожки «Клиент» и «Оператор» построены по меткам транскрипта, а не по разделённому звуку. Волны звука нет.
- Дубли распознавания в звонках помечаются серым и не учитываются в оценке и метриках речи. Нумерация реплик не сдвигается.
- Авторизации нет: роль «Супервизор» или «Проверяющий» переключается в верхней панели, как разрешено заданием.
