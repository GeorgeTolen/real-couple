# Промпт: этап 3 — техническая часть (бэкенд + движок оценки) CQA для Freedom Broker

> Отдай этот промпт целиком агенту-разработчику. Он самодостаточен.

---

## 0. Роль и цель

Ты — senior Python-инженер. За ~4 часа построй **бэкенд и движок оценки** прототипа Conversation Quality Analytics (CQA) для хакатона Freedom Broker. Интерфейс делается на следующем этапе — сейчас нужен работающий API, CLI и тесты. Код должен быть простым, читаемым и запускаться у жюри одной командой.

**Главная метрика хакатона:** точность AI-оценки относительно скрытого эталона (Ground Truth) на 10 новых транскриптах, которые выдадут за час до стоп-кода. Плюс: функциональность, удобство, **честность процесса** (система реально анализирует новые диалоги и применяет заданный чек-лист, никакого хардкода результатов), разнообразие архитектур (локальные и облачные LLM). Каждое решение принимай с оглядкой на эти критерии.

## 1. Контекст задачи (обязательные требования организаторов)

Контур 1 — оценка:
1. Пользователь создаёт/меняет чек-лист: критерии, формулировки, вес, тип ответа, доступность N/A, для числового критерия — шкала со ступенями. Новый критерий применяется **через настройки, без правки кода**. Конфигурация сохраняется.
2. Загрузка транскрипта, выбор чек-листа, запуск оценки оператора. Языки RU, KZ, EN. Реплики `bot` и `system` — контекст, оценивается только `operator`.
3. Результат по каждому критерию: ответ, баллы, вес, объяснение, реплика-доказательство. Если действие пропущено — указать проверенный участок разговора. При N/A — причина. Итог и результаты секций.

Контур 2 — работа с результатом:
4. Карточка: транскрипт + результат; ссылка из обоснования ведёт к нужному сообщению/фрагменту звонка; для звонка — прослушивание с переходом к таймкоду.
5. Апелляция: выбрать критерий, комментарий, сохранить. Проверяющий видит спорную оценку, комментарий и фрагмент.
6. Решение: проверяющий подтверждает или меняет оценку с причиной; система пересчитывает итог; доступны исходная оценка, решение и финальный результат.

На контроле организаторы попросят **заменить один критерий** через интерфейс и применить новый чек-лист к выданным диалогам. Авторизация не нужна. Для платной модели в README указать название и стоимость одной оценки со всеми вызовами.

Уточнение организаторов для звонков: логика та же, но критерии письменной речи адаптируются к устной. №6 для звонков — логичность ведения разговора, понятность объяснений, отсутствие неуместных выражений, корректность речевых формулировок, управление паузами; при наличии аудио — темп, дикция, разборчивость. №4 — ответил ли оператор на вопросы, не дал ли ошибочной информации, объяснил ли необходимые действия. Справочника эталонных ответов нет.

## 2. Данные

API организаторов: `GET <ORGANIZER_API_URL>&group_id=<ID>` (полный URL с подписью берётся из `.env`, `group_id` подставляется; DEV = `DEV`, контрольный id сообщат позже). Ответ:
```json
{"error":"","isSuccess":true,"data":{"dataset_group_id":"DEV","total_records":65,"records":[
 {"conversation_id":"p1-ru-001","channel":"agent chat","language":"RU",
  "transcript":[{"timestamp":"00:02","speaker":"operator","text":"Здравствуйте!"}],
  "audio_url":null}]}}
```
Факты, проверенные на DEV (`data/dev.json` уже скачан):
- 65 записей: 60 чатов (30 RU, 15 KZ, 15 EN) + 5 звонков `voice call` RU (`p4-ru-001..005`). Роли: client, operator, bot, system. Средний чат ≈ 20 реплик / 1.3k символов, максимум 115 реплик.
- Время: чаты `MM:SS`, звонки ISO 8601 с часовым поясом. **Исходные метки сохранять**, дополнительно хранить `t_sec` от начала диалога.
- `audio_url` звонка возвращает **HTML-страницу плеера**, а не mp3. В ней `<source src="https://...dynamics.com/api/filedownload/...&sig=...">` — SAS-ссылка на mp3, живёт ~1 час. Нужно: на каждый запрос аудио заново получить HTML, вытащить `src` (раскодировать `&amp;`), скачать mp3 и закешировать на диск (`data/audio/<conversation_id>.mp3`). mp3: моно, 16 кГц, ~6.5 мин.
- В диалогах намеренно заложены нарушения: оператор не представился, «Привет» вместо приветствия, переспросил известное боту, раскрыл данные счёта без идентификации, предложил платную консультацию по личному номеру, закрыл чат без прощания и т. п.

## 5. Модель чек-листа (конфигурация = источник правды)

```jsonc
{
  "id": "freedom-default", "version": 1, "name": "Freedom Broker — чаты и звонки",
  "sections": [{"id": "start", "title": "Начало и понимание запроса"}, ...],
  "criteria": [
    {
      "id": "c1", "section": "start", "title": "Установление контакта",
      "type": "binary",               // binary | scale | flag
      "allow_na": false,
      "weight": 10,                   // flag → вес 0, не входит в баллы
      "description": "Да — оператор поздоровался на языке клиента и представился в первом ответе.",
      "na_condition": null,
      "scale": null,                  // для scale: [{"value":20,"label":"..."},{"value":15,...}], max = наибольшее value
      "channel_overrides": {          // необязательно: иная формулировка для голосового канала
        "voice call": {"description": "..."}
      },
      "guidance": "Подсказки судье: что считать представлением, типичные ошибки"   // необязательно, для калибровки
    }
  ]
}
```
Заведи `freedom_default.json` дословно по PDF-чек-листу организаторов (тексты ниже) **плюс** `channel_overrides` для `voice call` у c4 и c6 по уточнению организаторов из п.1. Версии неизменяемы: любое редактирование = новая версия; оценка хранит `checklist_id + version`.

Тексты критериев (из PDF):
- c1 Установление контакта · ДА/НЕТ · 10 — Да: поздоровался на языке клиента и представился в первом ответе.
- c2 Выявление потребности · ДА/НЕТ/N/A · 15 — Да: учёл известные детали и уточнил недостающее до ответа. N/A: данных для ответа хватало с самого начала.
- c3 Идентификация · ДА/НЕТ/N/A · 20 — Да: проверка личности подтверждена до раскрытия данных или защищённого действия. N/A: запрос не требовал идентификации. Если требовалась и не подтверждена в чате — Нет.
- c4 Корректная и полная консультация · 0–20/N/A · 20 — 20 все существенные вопросы закрыты или дан корректный следующий шаг; 15 основной решён, пропущена второстепенная деталь; 10 часть закрыта, существенный вопрос открыт; 5 общая подсказка, клиенту непонятно, как действовать; 0 ответа по существу нет или ключевая рекомендация ошибочна. N/A: чат закончился до того, как клиент сформулировал запрос.
- c5 Эмпатия и клиентоориентированность · ДА/НЕТ · 15 — Да: вежлив и, если клиент выразил недовольство или описал неудобство, отреагировал на конкретную проблему.
- c6 Управление диалогом, скорость и грамотность · 0–10 · 15 — 10 ясные и связные ответы, при явном ожидании предупредил; 7 один заметный сбой, клиент может понять и продолжить; 4 клиенту приходится переспрашивать из-за формулировок или порядка ответов; 0 бессвязные/противоречивые реплики, ход диалога непонятен.
- c7 Завершение · ДА/НЕТ/N/A · 5 — Да: подвёл итог или предложил дальнейшую помощь и попрощался. N/A: чат оборвался до возможности завершить.
- c8 Грубые ошибки · ДА/НЕТ · без баллов — Да: оскорбление клиента, предложение платной услуги в обход компании (перевести деньги лично / личный номер для платной консультации — достаточно самого предложения) или раскрытие конфиденциальной информации.
- В этом задании порог первой реакции 3 минуты, теги и вложения в оценку **не входят**.
- Отличие «Нет» от N/A: «Нет» — действие было нужно, но пропущено/сделано неправильно; N/A — неприменимо по условию.
- Консультация (c4) = правильно и полно ли решён запрос; ведение диалога (c6) = насколько понятно и последовательно общался. Ясный ответ на один из двух важных вопросов → высокий c6 и частичный c4.

## 6. Расчёт баллов (`scoring.py`, чистые функции, 100% покрыть тестами)

1. Применимость: N/A допустим только если `allow_na`. Если судья вернул NA там, где нельзя, — это ошибка валидации → повторный запрос/арбитр.
2. Доля `f`: binary Да=1, Нет=0; scale `value/max` (верхняя ступень = полный вес); flag не участвует.
3. Итог = `Σ(weight·f) / Σ(weight применимых) × 100`, если применимых с весом нет → `null` («не рассчитывается»).
4. Округление до 2 знаков **половина вверх** (`Decimal.quantize(ROUND_HALF_UP)`), вынести в константу `ROUNDING_MODE` — организаторы могут уточнить.
5. Секции: та же формула внутри секции. Грубые ошибки — отдельный флаг `gross_violation: bool` + список.
6. Для отчёта по каждому критерию: `max_points` (вес после перераспределения), `earned_points`, `weight`, `normalized_weight`.

Обязательные тест-кейсы (стандартный чек-лист):
- p1-ru-009: c1 Y, c2 Y, c3 N, c4 5, c5 N, c6 4, c7 Y, c8 Y → `41.00`, gross = true.
- p1-ru-020: c1 Y, c2 NA, c3 NA, c4 20, c5 Y, c6 10, c7 N, c8 N → применимые веса 65, набрано 60 → `92.31`.
- Все применимые N/A, кроме критериев без N/A — проверить, что знаменатель корректен; вариант «все NA» на кастомном чек-листе → `null`.
- Кастомный чек-лист с новым scale-критерием 0–3 → корректная доля.

## 7. Движок оценки

### 7.1 Нормализация и рендер
Каждая реплика: `idx` (с 0), `speaker`, `timestamp` (как пришло), `t_sec`. Для промпта:
```
conversation_id: p1-ru-009 | канал: agent chat | язык: RU
[#9] 01:51 operator: Здравствуйте, я Руслан. ...
```
Для звонков в промпте показывать относительное время `mm:ss` от начала + исходник хранить.

### 7.2 Детерминированные сигналы (`signals.py`)
Не выносят вердикт, а **добавляются в промпт блоком «Факты, посчитанные системой»** и сохраняются в результат: индекс первой реплики оператора; ответил ли бот до оператора; время от эскалации до первой реплики оператора; паузы оператора > 60 с (и > 180 с — порог первой реакции); последняя реплика в диалоге и кто её автор; системное событие закрытия чата и кем; есть ли в первой реплике оператора приветственное слово (словари RU/KZ/EN) и вероятное имя. Для звонков — метрики из `audio.py` (если аудио доступно).

### 7.3 Компиляция промпта и схемы (`prompt_builder.py`)
Из версии чек-листа и канала диалога генерируй:
- **system prompt** (RU, единый для всех языков диалога): роль QA-эксперта Freedom Broker; оценивается только operator; правила Да/Нет/N/A; полный текст каждого критерия (с учётом `channel_overrides`) с id, типом, ступенями, условием N/A, `guidance`; требование ссылаться на номера реплик; для пропущенного действия — указать проверенный участок; reasoning коротко (≤ 3 предложения) на русском; **сначала доказательства и рассуждение, потом ответ**.
- **JSON Schema** (strict), поле на каждый критерий:
  `{"evidence_ids": int[], "checked_range": [int,int] | null, "reasoning": str, "answer": enum}`; `answer` enum строится из типа: binary → `["Y","N"]` (+`"NA"` если allow_na), scale → строки ступеней (+`"NA"`), flag → `["Y","N"]`.
- Хеш промпта (`prompt_version`) сохраняй в оценке.
Добавление/замена критерия в конфиге автоматически меняет и промпт, и схему, и расчёт — это ключевое требование контроля, покрой тестом.

### 7.4 LLM-клиент (`llm.py`)
- `POST {base_url}/chat/completions`, `response_format: {type: json_schema, strict: true}`, `temperature: 0`, для OpenRouter `usage: {include: true}` (в ответе `usage.cost` в $) и `reasoning: {effort: "medium"}`.
- Если провайдер не поддерживает json_schema (локальные), фоллбэк: `response_format: {type: "json_object"}` + схема в промпте + валидация pydantic + до 2 повторов с текстом ошибки.
- Ретраи с экспоненциальной паузой на 429/5xx/402 (`in_flight_budget_exhausted` у OpenRouter = слишком много параллельных запросов), таймаут 180 с, `asyncio.Semaphore` (по умолчанию 4). Логируй модель, токены, стоимость, латентность. Ключ — только из `.env`, в логи не писать.
- Модели знать по имени из конфига, не хардкодить в логике.

### 7.5 Ансамбль (`judge.py`)
Режимы оценки (выбираются в запросе):
- `single` — один судья.
- `ensemble` (по умолчанию) — судьи A и B параллельно; по каждому критерию: совпали → ответ, `agreement: "full"`; разошлись → вызвать арбитра **только по спорным критериям** (передать оба ответа с доказательствами и транскрипт), `agreement: "arbitrated"`, флаг `needs_review: true`. Если арбитр недоступен — консервативное правило (для binary — ответ судьи с более сильными доказательствами нельзя определить программно, поэтому берём ответ судьи A и ставим `needs_review`), для scale — меньшее из значений + `needs_review`.
- `local` — один локальный судья (Ollama).
Пресеты по умолчанию (по бенчмарку, см. ниже): A = `google/gemini-3.8-flash`, B = `openai/gpt-6.1-sol`, арбитр = `google/gemini-4-argon`; local = Gemma 4 26B-A4B через Ollama (тег модели — из конфига). Всё переопределяется в `.env`/запросе.
Страховка от пропуска грубой ошибки (Gemini 3.8 Flash дважды пропускал c8 при раскрытии данных без идентификации): если итог c3 = N и c8 = N у кого-то из судей — c8 считается спорным и уходит арбитру.

### 7.6 Хранение результата оценки
`evaluation`: id, conversation_id, checklist_id, checklist_version, mode, models, prompt_version, status, created_at, total_score, sections_json, gross_violation, needs_review, cost_usd, tokens_in/out, latency_ms, signals_json.
`criterion_result`: evaluation_id, criterion_id, answer, earned_points, max_points, weight, reasoning, evidence_ids, checked_range, na_reason, agreement, judge_answers_json (сырые ответы каждого судьи), source = `ai`.
Сырые ответы моделей хранить целиком (нужно для апелляции и для доказательства «честности процесса»).

## 8. Апелляции
- `appeal`: id, evaluation_id, criterion_id, comment, author, status (`open|resolved`), created_at.
- `decision`: appeal_id, reviewer, action (`confirm|change`), new_answer, reason, created_at.
- При `change` создаётся **финальный слой**: исходная AI-оценка неизменна, итог пересчитывается с подменой ответа критерия (`source = "reviewer"`). Эндпоинт карточки отдаёт `original`, `decisions[]`, `final`.
- Опционально (если успеешь): «перепроверить AI» по апелляции — вызвать арбитра по одному критерию с комментарием оператора как дополнительным контекстом и показать его мнение проверяющему (решает человек).

## 9. Аудио (`audio.py`)
- `GET /api/conversations/{id}/audio` — отдаёт mp3 (`audio/mpeg`) с поддержкой `Range` (для перемотки в `<audio>`), из кеша или резолвит заново.
- Метрики (если есть ffmpeg и mp3): длительность; паузы (`ffmpeg -af silencedetect=noise=-35dB:d=1.5`); по транскрипту: темп оператора = слова реплик оператора / время его реплик (оценка по таймстемпам соседних реплик), доля речи оператора, число длинных пауз внутри разговора, перебивания (реплики с интервалом < 1 с после чужой). Отдавать числа + интерпретацию («темп в норме 110–170 сл/мин») в сигналы c6 для звонков. Не выдумывать дикцию — без ASR её не оцениваем, честно писать «по аудио: темп и паузы».

## 10. API (FastAPI, всё под `/api`, JSON, OpenAPI доступен на `/docs`)
- `GET /health`
- `POST /datasets/import` `{group_id}` → импорт/обновление (upsert по conversation_id) из API организаторов; `POST /conversations/upload` (файл в формате API или массив records).
- `GET /conversations?language=&channel=&status=&needs_review=&gross=&q=` (с последней оценкой: итог, флаги) · `GET /conversations/{id}` (транскрипт + последняя оценка) · `GET /conversations/{id}/audio` · `GET /conversations/{id}/audio-metrics`
- `GET /checklists` · `GET /checklists/{id}` (последняя версия + список версий) · `POST /checklists` (создать) · `POST /checklists/{id}/versions` (новая версия из полного JSON) · `POST /checklists/{id}/criteria/{cid}/replace` (удобный эндпоинт «заменить критерий» = новая версия) · валидация: уникальные id, веса ≥ 0, у scale есть ступени, flag с весом 0.
- `POST /evaluations/run` `{conversation_ids|"all", checklist_id, version?, mode, models?}` → `job_id` · `GET /jobs/{id}` (прогресс, ошибки, стоимость) · `GET /evaluations/{id}` (полный результат: original + final + decisions) · `GET /evaluations?conversation_id=&checklist_version=`
- `POST /evaluations/{id}/appeals` · `GET /appeals?status=open` (с фрагментом диалога вокруг доказательств) · `POST /appeals/{id}/decision`
- `GET /export/results?format=csv|json&checklist_version=` — по диалогу: id, ответы по критериям, итог, gross, модель, стоимость (для сдачи контроля).
- `GET /models` (пресеты и доступность провайдеров) · `GET /stats` (сводка: средний балл, по языкам/критериям, стоимость).

6. Апелляции + пересчёт; тест полного сценария `test_api_flow.py`: импорт → оценка (с моком LLM) → апелляция → решение «change» → итог изменился, original сохранён.

8. Экспорт, `/stats`, `/models`, README (запуск за 3 команды, переменные, модели и стоимость одной оценки, архитектура одной схемой), Dockerfile, Makefile.

## 15. Запреты и подводные камни
- Никаких предзаполненных результатов по conversation_id, никаких правил вида «если id == ...». Few-shot примеры в промпте — только синтетические или с обезличенным текстом, не id из DEV.
- LLM не считает баллы — только выбирает ответ/ступень. Расчёт и перераспределение весов — код.
- Не терять исходные таймстемпы; не путать индекс реплики и время.
- Не коммитить `.env`, ключи, sqlite, аудио-кеш.
- OpenRouter: следи за бюджетом; кешируй ответы по ключу `(conversation_hash, prompt_version, model)` — повторный прогон без изменений не должен тратить деньги.
- Ответы моделей иногда приходят в ```json-обёртке или с пустым `content` — обработать, повторить.
- Всё, что ты не успел, перечисли в конце README в разделе «Ограничения».
