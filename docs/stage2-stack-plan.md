# Этап 2б — стек и архитектура (2026-11-07, 15:30)

## Факты, на которые опирается выбор
- DEV: 65 записей = 60 чатов (30 RU, 15 KZ, 15 EN) + 5 звонков RU (p4-ru-001..005). Чат ≈ 1.3k символов, ≤ 115 реплик.
- `audio_url` звонка → HTML-страница плеера; внутри `<source src>` — mp3 в Dynamics с SAS-ссылкой, живёт ~1 час. mp3 моно 16 кГц, ~6.5 мин. ⇒ бэкенд каждый раз заново достаёт свежую ссылку и проксирует/кеширует mp3.
- Таймстемпы: чаты `MM:SS`, звонки ISO 8601 ⇒ нормализуем в секунды от начала, исходник сохраняем.
- Бенчмарк (stage2-model-selection.md): Gemini 3.8 Flash + GPT-6.1 Sol — лучшие; слабые места — c4 и c6.
- Dynamics 365: PCF «virtual» компоненты = React + Fluent UI из платформы (React 16.14/17, Fluent 8/9). Также доступен HTML web resource / iframe.

## Движок оценки
1. Загрузка: API организаторов (group_id из UI) или ручная загрузка JSON → нормализация, нумерация реплик `[#N]`.
2. Детерминированные сигналы (подсказки модели, не вердикт): первая реплика оператора, есть ли имя, последняя реплика оператора, системное «оператор закрыл чат», паузы > 60 с, жалобы клиента, бот ответил первым.
3. LLM-судьи: промпт и JSON-схема **генерируются из конфигурации чек-листа** (любые критерии, типы Да/Нет, Да/Нет/N/A, шкала с ступенями, описания ступеней, условия N/A, отдельная версия для звонков). Порядок полей: evidence_ids → reasoning → answer.
4. Ансамбль: судья A (Gemini 3.8 Flash) + судья B (GPT-6.1 Sol) параллельно. Совпали → ответ. Расходятся → арбитр (Gemini 4 Argon) или флаг «на ручную проверку». Показываем уверенность.
5. Баллы только в коде: шкала → доля веса, N/A → пропорциональное перераспределение до 100, округление до 2 знаков, секции, грубые ошибки отдельно.
6. Апелляция: критерий + комментарий → проверяющий видит спорную оценку и фрагмент → подтверждает/меняет с причиной → пересчёт; хранятся исходная оценка, решение, финальный результат.
7. Логи: модель, токены, стоимость каждой оценки (требование гайда про платные модели).
